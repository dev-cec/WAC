\chapter{La démarche}

\section{Pourquoi un JSON valide ne prouve rien}

\wac{} produit des fichiers JSON destinés à une expertise. Qu'ils soient
valides ne dit presque rien de leur justesse : un champ lu au mauvais décalage,
une date interprétée dans le mauvais fuseau, un nom décodé dans la mauvaise
page de code, une décompression fausse donnent tous un JSON parfaitement
valide, et faux. Les défauts les plus graves relevés dans \wac{} étaient tous de
cette sorte. Aucun ne se voyait à l'exécution ; chacun n'est apparu qu'en
confrontant une valeur à une \textbf{source indépendante}.

La validation de \wac{} repose donc sur ce principe : toute donnée qui peut
être recoupée l'est, par un moyen qui ne partage rien avec le code vérifié.

\section{Quatre niveaux de contrôle}

\begin{description}[leftmargin=0pt,itemsep=0.5em]
  \item[Les contrôles intégrés à \wac{}] (chapitre~\ref{ch:integres}) :
    exécutés à chaque collecte, sur la machine examinée. Ils refusent une
    donnée incohérente plutôt que de la publier, et attestent l'intégrité des
    pièces prélevées.
  \item[Les programmes de test] (chapitre~\ref{ch:harnais}) : seize
    exécutables qui confrontent chaque décodeur à une référence (la fonction de
    Microsoft qu'il remplace, une norme publiée, une autre implémentation), ou
    qui prouvent qu'un analyseur ne lit jamais hors de son tampon.
  \item[Le cycle automatique et ses contrôles] (chapitre~\ref{ch:cycle}) : une
    collecte complète dans une machine virtuelle Windows~11, puis
    \fichier{check-json.py}, qui vérifie la validité des sorties et les
    confronte entre elles et à des sources externes.
  \item[Les recoupements sur une collecte réelle] (chapitre~\ref{ch:reel}) :
    ce qu'une machine virtuelle neuve ne contient pas (journaux anciens,
    fichiers fragmentés, noms exotiques) est vérifié sur les données d'une
    vraie machine, traitées en local.
\end{description}

\section{Les règles de développement qui s'y rattachent}

\begin{enumerate}
  \item \textbf{Un correctif s'accompagne du test qui aurait pris le défaut},
    et ce test est vérifié dans les deux sens : il passe sur le code corrigé,
    et il échoue quand on réintroduit le défaut. Un test qui n'a jamais été vu
    échouer ne prouve rien.
  \item \textbf{La compilation se fait sans avertissement}, options
    \texttt{-Wall -Wextra} activées. Les avertissements ont d'ailleurs servi
    de liste de travaux : chacun signalait un champ décodé puis perdu.
  \item \textbf{Après toute modification, la nouvelle collecte est comparée à
    la précédente}, artefact par artefact : un artefact passé de 1~522 entrées
    à 573 n'allume aucun voyant, seule la comparaison le montre.
  \item \textbf{Toute entrée est hostile}, y compris un fichier du disque
    examiné : chaque lecture est bornée par la taille réelle du tampon, jamais
    par une longueur annoncée dans la donnée.
  \item \textbf{Un champ sans valeur n'est pas émis} : une clé vide ou nulle se
    lirait comme une donnée relevée, ou comme une lecture ratée.
\end{enumerate}

% ============================================================ 2
\chapter{Les contrôles intégrés à WAC}\label{ch:integres}

Ces contrôles font partie du programme de collecte. Ils s'exécutent à chaque
collecte et leur résultat est consigné dans \fichier{investigation.json},
opération par opération, avec son code de retour et la trace qu'elle laisse
sur le système examiné.

\section{Avant toute extraction}

\begin{itemize}
  \item version de Windows (10 ou ultérieure) et droits d'administrateur
    effectifs (jeton élevé) ;
  \item emplacement de collecte utilisable et place disponible, vérifiés
    \emph{avant} la première extraction : une collecte interrompue faute de
    place laisserait une consigne incomplète.
\end{itemize}

\section{Lecture brute du volume NTFS}

Les fichiers verrouillés (ruches, journaux) sont lus directement sur le volume,
sans passer par le système de fichiers de Windows. Chaque structure lue est
vérifiée avant d'être utilisée :

\begin{itemize}
  \item signature \texttt{FILE} de chaque enregistrement de la \fichier{\$MFT}
    et \texttt{INDX} de chaque bloc d'index, puis vérification des
    \emph{fixups} (tableau de séquence de mise à jour) : chaque tranche de
    512~octets doit se terminer par le numéro de séquence de l'enregistrement.
    Un enregistrement \emph{déchiré} par une écriture interrompue, mélange de
    deux versions, est refusé au lieu d'être lu comme une donnée plausible ;
  \item décompression LZNT1 et WOF bornée par la taille attendue de chaque
    unité : une unité qui ne produit pas le nombre d'octets prévu est une
    erreur, pas une donnée tronquée en silence ;
  \item taille extraite comparée à la taille déclarée par l'attribut
    \texttt{\$DATA} : leur écart, publié dans le manifeste, révèle une
    extraction tronquée qu'une empreinte seule ne montrerait pas ;
  \item attributs cherchés aussi dans les enregistrements d'extension
    (\texttt{\$ATTRIBUTE\_LIST}) : un répertoire dont NTFS a déplacé le
    \texttt{\$INDEX\_ROOT}, cas de milliers de composants WinSxS, était
    déclaré illisible (4~569 répertoires d'un Windows~11) ;
  \item blocs d'index libérés ignorés, d'après le \texttt{\$BITMAP} de
    l'index : ils peuvent garder des entrées périmées ;
  \item chaque lecture d'attribut bornée par la taille réelle de l'attribut,
    \texttt{\$STANDARD\_INFORMATION} compris ;
  \item dates du fichier source relevées dans \texttt{\$STANDARD\_INFORMATION}
    \emph{et} dans \texttt{\$FILE\_NAME} : un programme qui falsifie les
    premières (\emph{timestomping}) ne touche pas les secondes, et l'écart se
    voit au manifeste.
\end{itemize}

\section{Ruches du registre}

\wac{} lit les ruches avec son propre lecteur, lié dans l'exécutable, et non
avec une bibliothèque de la machine examinée.

\begin{itemize}
  \item bloc de base : signature \texttt{regf}, somme de contrôle (OU exclusif
    des 127 premiers mots), numéros de séquence primaire et secondaire. Une
    ruche dont les journaux n'ont pas été rejoués est \textbf{refusée} : lue
    telle quelle, elle donnerait des clés périmées sans aucune erreur ;
  \item rejeu des journaux de transactions (\texttt{.LOG1}/\texttt{.LOG2}) :
    signature et chaînage des séquences de chaque entrée ; une entrée hors
    chaîne est écartée et comptée ; un journal d'annulation est écrit avant
    toute modification, pour pouvoir reconstituer la copie brute ;
  \item chaque décalage lu dans la ruche est vérifié contre la taille réelle du
    fichier, et une sous-clé qui pointerait vers l'une de ses ancêtres est
    refusée : un parcours ne peut pas boucler sur une ruche forgée.
\end{itemize}

\section{Intégrité des pièces : la consigne}

Toute pièce extraite est déposée dans une \emph{consigne} qui n'est plus jamais
rouverte en écriture ; tout le travail se fait sur une seconde copie.

\begin{itemize}
  \item trois empreintes par pièce (MD5, SHA-1, SHA-256), calculées pendant la
    lecture du volume ;
  \item la copie de travail est vérifiée par son SHA-256 contre ce qui a été
    lu sur le volume, et non contre une relecture de la consigne ;
  \item le manifeste qui identifie les pièces est scellé par un second fichier
    portant son empreinte : un manifeste retouché se détecte ;
  \item un échec d'extraction est consigné lui aussi : une pièce absente du
    manifeste se lirait comme jamais cherchée ;
  \item les dates d'un artefact fichier (Prefetch, raccourci, liste de sauts)
    sont celles du fichier source, relevées au manifeste, jamais celles de la
    copie de travail, qui sont celles de la collecte ;
  \item une conversion séparée (\opt{convert}) vérifie le sceau et le
    SHA-256 de chaque pièce \emph{avant} toute lecture, refuse la consigne au
    premier écart, et n'accepte que des chemins de pièces qui restent dans la
    consigne.
\end{itemize}

Un tiers peut vérifier la consigne sans \wac{}, avec les scripts
\fichier{verify-exhibits.ps1} (messages en anglais) et
\fichier{verifier-consigne.ps1} (messages en français), livrés avec la
documentation utilisateur : ils contrôlent le sceau puis l'empreinte de chaque
pièce ; un binaire authentifié lu mais non copié (« empreinte seule ») est
compté à part, faute de fichier.

\section{Authenticité des binaires}

Avec l'option \opt{binary}, \wac{} prélève les binaires cités par les
artefacts, sauf ceux dont il établit qu'ils sont signés par Microsoft. Cette
décision repose sur une vérification complète, faite par \wac{} lui-même :
signature RSA de chaque catalogue de sécurité, chaîne de certificats jusqu'à
une racine Microsoft, empreinte Authenticode du fichier retrouvée dans un
catalogue vérifié, ou signature intégrée. Les catalogues lus sont ceux de
\path|CatRoot|, des composants (\path|WinSxS\Catalogs|) et des paquets de
maintenance ; les signataires acceptés, ceux de Microsoft pour son propre code,
\texttt{.NET} compris. Les fichiers d'une application du Store sont vérifiés par
la signature de leur paquet et la carte de ses blocs, bloc de 64~Kio par bloc.
Un fichier dont l'authenticité n'est pas établie est prélevé : le doute conduit
à collecter, jamais à écarter. Les catalogues, signatures et cartes qui ont
justifié un non-prélèvement sont consignés ; chaque PE porte au manifeste sa
version (\texttt{TimeDateStamp}, \texttt{SizeOfImage}), clé du serveur de
symboles de Microsoft qui permet d'en retrouver le contenu identique. Avec
\opt{binary-all}, tout est prélevé, et le verdict est consigné pour chaque
exécutable.

\section{Journaux d'événements}

Signature du fichier, de chaque bloc (\emph{chunk}) et de chaque
enregistrement. Tous les blocs physiques du fichier sont parcourus, et pas
seulement ceux que l'en-tête déclare : un journal mal fermé livre ainsi les
enregistrements qu'il ne compte pas. Un bloc illisible est signalé et sauté ; il
n'interrompt plus la lecture du fichier.

\section{Décodage des artefacts}

\begin{itemize}
  \item toute lecture est bornée par la taille du tampon ; un nombre
    d'éléments déraisonnable dans une liste de valeurs (au-delà de 65~536) est
    refusé plutôt que parcouru ;
  \item une date impossible (mois~13, heure~25) ou hors de la plage d'un
    \texttt{FILETIME} donne une date absente, donc non émise, et jamais une
    valeur quelconque ;
  \item chaque date locale porte le décalage en vigueur \emph{à sa date},
    selon les règles d'heure d'été de la machine examinée, année par année ;
  \item les SID sont nommés à partir des preuves seules (SAM, SID bien connus,
    SID de services, profils), jamais en interrogeant le système ou le réseau :
    \texttt{LookupAccountSidW} interrogeait le contrôleur de domaine pour un
    SID inconnu de la machine, une trace de la collecte sur une autre machine.
    La compilation échoue si \fichier{WAC.exe} importe une fonction de
    résolution de noms ;
  \item un GUID inconnu de la table de référence est nommé d'après les ruches
    de la machine examinée (classes de la machine, dossiers connus, classes de
    chaque utilisateur) ; inconnu partout, il est publié sans nom, jamais avec
    un texte de remplacement.
\end{itemize}

\section{Conversions : le détail de \texttt{system\_conversions\_test}}

\wac{} ne dépend que de cinq bibliothèques système (\fichier{ADVAPI32},
\fichier{KERNEL32}, \fichier{msvcrt}, \fichier{Secur32}, \fichier{WTSAPI32}),
nécessaires pour interroger le système en marche. Les conversions qu'il
demandait autrefois à d'autres bibliothèques de la machine examinée sont faites
par son propre code, et ce programme les confronte aux fonctions de Windows
qu'elles remplacent :

\begin{itemize}
  \item SID de services, calculés hors ligne, comparés à
    \texttt{LookupAccountNameW} pour les 273 services de la machine ;
  \item GUID, SID dans les deux sens, dates OLE, noms de propriétés (table de
    1~698 entrées générée depuis le schéma de Windows) ;
  \item dates FAT, sur toutes les dates possibles ;
  \item heure d'été : décalage dans les deux sens sur les \textbf{141 fuseaux}
    de Windows, avec leurs règles année par année, à chaque transition de 1980
    à 2035 (heure sautée, heure répétée, changement de règle au 1\textsuperscript{er}
    janvier) ;
  \item lecture de la clé \fichier{TimeZoneInformation}, comparée à
    \texttt{GetTimeZoneInformation} ;
  \item règles de fuseau forgées au hasard : aucun débordement.
\end{itemize}

Écarts voulus, et documentés : \wac{} refuse un SID écrit que Windows
tronquerait, et une date OLE non numérique pour laquelle Windows rend une heure
dénuée de sens.

\section{Harnais de robustesse}

Un analyseur lit à des positions que le fichier déclare lui-même. Sur un
fichier tronqué ou forgé, une lecture hors tampon ne plante pas d'elle-même :
elle lit la mémoire voisine et la publie, dans un JSON valide. Les harnais de
robustesse la font planter : chaque entrée est placée contre une page mémoire
interdite, une fois à sa fin, une fois à son début. Un seul octet lu hors de
l'entrée arrête le test. Un chien de garde arrête aussi un analyseur qui ne
termine pas.

Chaque fichier est analysé entier, dans ses troncatures, et en copies
corrompues au hasard (graine fixe : un échec se reproduit à l'identique).

\chapter{Le cycle automatique et ses contrôles}\label{ch:cycle}

\section{Le cycle}

\fichier{vmtest/run-wac-test.sh} exécute, sans aucune intervention, une
collecte complète dans une machine virtuelle Windows~11 (vrai NTFS, vrai
registre) :

\begin{enumerate}
  \item avec \opt{build}, compilation sans avertissement de \wac{} et des
    programmes de test ;
  \item validation de l'extraction brute d'une ruche : \texttt{reg load} doit la
    refuser avant réparation et l'accepter après ;
  \item exécution de \wac{} avec les droits SYSTEM ; le code de retour est
    vérifié, et la trace est cherchée pour toute exception non traitée ;
  \item rapatriement des sorties, du journal de collecte et de la liste des
    fichiers réellement présents dans la consigne ;
  \item exécution de \fichier{check-json.py} ;
  \item collecte seule (\opt{collect} \opt{events} \opt{binary}, ou
    \opt{binary-all}), qui ne doit rien convertir ; vérification de la consigne
    par \fichier{verify-exhibits.ps1} ; conversion d'une consigne dont une pièce
    a été retouchée, qui doit être refusée avant toute lecture ; conversion,
    contrôlée par \fichier{check-json.py} ; seconde conversion, dont les JSON
    doivent être identiques à la première, octet pour octet.
\end{enumerate}

\section{Les contrôles de \texttt{check-json.py}}

Le script vérifie d'abord la validité JSON de chaque fichier et la forme des
chemins Windows (un double échappement se voit après analyse). Il confronte
ensuite des valeurs calculées par \wac{} à des valeurs indépendantes : une
autre donnée de la même collecte, ou une source externe. Chaque contrôle
ci-dessous a été écrit après un défaut réel, qu'il a pris.

\section{Résultat de référence}

Dernier cycle, le 25 septembre 2026, sur la version 1.3.1 (Windows~11, fuseau
de Paris), sans aucun échec ni avertissement :

\begin{itemize}
  \item \textbf{exécution complète} (\opt{events} \opt{binary}, 4~min~33~s) :
    24 fichiers JSON valides sur 24 produits, USBSTOR compris (le harnais
    branche une clé USB virtuelle à chaque cycle, si bien qu'une machine de
    test recréée la connaît aussi) ; 62 contrôles passés, dont 4~090 dates
    locales confrontées à la base IANA et 170~344 événements décodés dans
    404 journaux ; 1~640 pièces, exactement celles du manifeste, sceau conforme ;
  \item \textbf{collecte seule} (\opt{collect} \opt{events} \opt{binary},
    16~min~39~s) : rien converti ; 43~513 exécutables lus, 27~958 authentifiés et non
    copiés, 12~700 fichiers différentiels de Windows, 2~508 prélevés (676~Mo) ;
    6~461 pièces vérifiées par \fichier{verify-exhibits.ps1} ; une pièce
    retouchée refusée avant toute lecture ;
  \item \textbf{conversion} (\opt{convert}, 43~s) : 75 contrôles passés, dont

  \item \textbf{\opt{binary-all}} (cycle précédent) : 58~509 exécutables
    copiés, chacun avec le verdict de sa signature.

\chapter{Les recoupements sur une collecte réelle}\label{ch:reel}

Une machine virtuelle neuve ne produit ni fragmentation, ni listes de sauts
anciennes, ni noms de fichiers exotiques, ni journaux abîmés. Plusieurs
défauts ne se sont révélés que sur une vraie machine, confrontée à une source
indépendante :

\begin{longtable}{@{}L{5.4cm}L{9.6cm}@{}}
\toprule
\textbf{Recoupement} & \textbf{Ce qu'il a montré} \\
\midrule
\endhead
listes de sauts / \texttt{olefile} & les flux s'appellent « 1 » à « f »,
  et non « 01 » à « 0f » \\
cible d'un raccourci / entrée DestList & une page de code fausse et un chemin
  Unicode ignoré \\

\begin{note}
Une collecte réelle contient des données personnelles. Elle se traite en local ;

\end{note}

\chapter{Ce que ces contrôles garantissent}

\section{Garanties}

\begin{itemize}
  \item \textbf{Intégrité des pièces} : chaque pièce est identifiée par trois
    empreintes, la copie de travail est vérifiée contre la lecture du volume,
    le manifeste est scellé, et la consigne n'est jamais modifiée
    (\texttt{consigne\_test}, contrôles du cycle).
  \item \textbf{Aucune écriture sur le système examiné}, hors les traces
    inévitables d'une collecte sur un système en marche, toutes consignées dans
    \fichier{investigation.json} avec la trace attendue.
  \item \textbf{Exactitude des décodeurs} : pour ceux qui ont une référence
    (lecteur de ruches, décompressions, empreintes, conversions, fuseaux
    horaires, authenticité des binaires), résultats identiques à la référence
    sur les volumes indiqués.
  \item \textbf{Robustesse} : aucun analyseur de raccourcis, listes de sauts,
    Prefetch ou ruches ne lit hors de son tampon ni ne boucle, sur plus de deux
    millions d'entrées tronquées ou corrompues.
  \item \textbf{Cohérence des sorties} : chaque recoupement possible entre deux
    artefacts, ou entre un artefact et une source externe, est vérifié à chaque
    cycle.
  \item \textbf{Indépendance vis-à-vis de la machine examinée} : \wac{}
    n'emprunte à celle-ci aucune bibliothèque pour interpréter les preuves.
\end{itemize}

\section{Limites}

\begin{attention}
Ces contrôles ne prouvent pas l'absence de défaut. Ils prouvent que les défauts
qu'ils visent sont absents, sur les données qu'ils ont vues.
\end{attention}

\begin{itemize}
  \item \textbf{Complétude} : un artefact vide ne se distingue pas d'une
    machine sans trace. Seule la comparaison entre deux collectes, ou avec une
    machine dont on connaît le contenu, la mesure.
  \item \textbf{Données que la machine de test ne contient pas} :
    appareils MTP, fichiers éclatés sur plusieurs enregistrements de la
    \fichier{\$MFT} (\texttt{\$ATTRIBUTE\_LIST}), très gros volumes. Ils sont à
    valider sur des systèmes réels.
  \item \textbf{Artefacts sans référence} : quand aucun outil indépendant ne
    lit un format, sa justesse repose sur les recoupements internes et sur la
    documentation publique du format.
  \item \textbf{Fuseaux horaires} : la confrontation à la base IANA couvre les
    fuseaux dont les règles concordent avec celles de Windows sur la période
    vérifiée (Europe de l'Ouest, États-Unis, UTC) ; les autres sont vérifiés
    contre Windows seulement.
  \item \textbf{Compilation MSVC} : le projet Visual Studio est maintenu, mais
    les contrôles sont faits sur la version compilée par MinGW, celle qui est
    livrée.
\end{itemize}
