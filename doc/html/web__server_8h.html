Detailed Description

The web server of the examined machine: IIS (backlog B-035, lots 1 and 2), and the artefact's whole conversion; Apache, nginx and the database engines are read in web_installations.h (lot 3).

WHAT THE ARTEFACT PROVES. On a web server, a compromise goes through the site: a web shell dropped in its folder and the requests that call it, a native module added to IIS (a backdoor that sees every request, ATT&CK T1505.004), an application pool switched to a privileged identity. The configuration says what IIS runs and from where, the logs who asked for what, the site's folder what was dropped.

WHERE.

  • Windows\System32\inetsrv\config\applicationHost.config (IIS 7 and later, Vista and Server 2008 on): the sites, their bindings, their applications and virtual directories (physical path), the application pools and their identity, the native modules loaded in every worker (globalModules), the settings of the logs. Its earlier states are kept by IIS itself in inetpub\history\CFGHISTORY_<n> (configHistory, every two minutes after a change, ten kept): taken too.
  • IIS 5.1 and 6 (XP, Server 2003) keep it in inetsrv\MetaBase.xml: collected raw, not converted — no machine of the test cycle has it.
  • The logs: per site, <directory>\W3SVC<id>\u_ex<date>.log, the directory from the site's logFile, else siteDefaults', else SystemDrive%\inetpub\logs\LogFiles; those of HTTP.sys — requests refused before any site saw them — in Windows\System32\LogFiles\ HTTPERR. Each log folder is taken whole (its .log files), for the sites removed since.
  • The site's content: the folder of each virtual directory, taken whole, whatever its files (user decision of 2026-09-26: the code, the data, what an attacker dropped among them).
  • The application's databases: a site's web.config names them in its connection strings (|DataDirectory| is its App_Data). One inside a site's folder comes with it; one elsewhere is taken on its own, with its -wal and -journal, up to max_database_mib of wac.yml — a larger one is said, not copied (an engine's server, SQL Server or MySQL, is not a file: lot 3).
  • The application's accounts: in each SQLite database, a table whose name says accounts (users, wp_users, AspNetUsers, members…) and that has a password column; each row given, its hash with the scheme its form names (bcrypt, phpass, PBKDF2…), its other columns as {Column, Value} — a name from the database is never a JSON key. Judging a weak password is WAE's.

THE LOGS' FORMAT: W3C extended (w3c_log.h), IIS's default; the dates in UTC — IIS writes W3C in UTC whatever its localTimeRollover, which only names the files. The other formats (IIS, NCSA, custom) are taken raw, not converted.

OUTPUT. web_server_sites.json, web_server_application_pools.json, web_server_modules.json (the configuration, each element's attributes as IIS stores them — a password of a pool or a virtual directory stays as IIS encrypted it), web_server_logs.json (one object per request), web_server_connection_strings.json (each connection string as written: its password in clear when the site keeps it so; an encrypted section said by its provider, not decoded), web_server_accounts.json (one object per account row).
