Detailed Description

Outlook's data files, PST and OST, read with WAC's own code: the node and block layer (NDB) and the lists and tables built on it (LTP), after [MS-PST].

WHY OUR OWN READER. A mailbox holds the messages and the attachments an intruder sent or received; no Windows API reads a PST without Outlook, and WAC takes no library it does not review. The format is Microsoft's open specification [MS-PST]; what it leaves out was measured on the test corpus (backlog B-017) and is said where it is used.

WHAT IS READ.

  • The header: "!BDN", the version — 23 for a Unicode PST (Outlook 2003 and later), 36 for the OST of Outlook 2013 and later, with 4 KiB pages and compressed blocks —, the encryption, the roots of the two B-trees. The ANSI files (versions 14 and 15, Outlook 97 to 2002) are not decoded.
  • The node B-tree (NBT): a node per folder, message, attachment…, with its data, its subnodes and its parent; the block B-tree (BBT): where each block lies. Pages of 512 bytes (version 23) or 4,096 (36).
  • The blocks: their trailer, the "permutation" encryption undone; in version 36, a block whose stored size is not its inflated size is a zlib stream, inflated and its Adler-32 checked. The "cyclic" encryption has no sample to check it on: refused, and said.
  • The data trees (XBLOCK, XXBLOCK) and the subnode trees (SLBLOCK, SIBLOCK).
  • On top: the heap on a node (HN), the B-tree on a heap (BTH), the property context (PC: a message, a folder, an attachment) and the table context (TC: recipients, attachments).

HOSTILE INPUT. A PST is the suspect's file: every offset, count and size read in it is checked against the file and the block it lies in; a cycle in a tree is stopped by a depth limit. A part that does not hold is left out, and the rest still read.
