Detailed Description

Offline reader of the WMI repository (CIM): \Windows\System32\wbem\Repository.

WHY OFFLINE. Querying WMI runs code on the examined machine and leaves its own traces; a subscription an intruder planted is precisely what a live query may be steered around. The repository's files, copied raw, say what WMI would load, without WMI.

THE FORMAT (Vista and later), described by FireEye's FLARE team ("WMI Offense, Defense, and Forensics", 2015; python-cim) and checked on the test VM against Get-CimInstance:

  • MAPPING1..3.MAP: the one with the highest version maps the logical pages (0x2000 bytes) of OBJECTS.DATA, then those of INDEX.BTR, to physical ones;
  • INDEX.BTR: a B-tree of keys, "NS_<hash>/CI_<hash>/IL_<hash>.<page>.<id>.<size>", each part a prefix and the SHA-256 of an upper-case UTF-16 name (namespace, class, instance); the last part locates the record;
  • OBJECTS.DATA: each page starts with a table (record id, offset, size, CRC); a record larger than its page continues on the next logical pages;
  • a class definition (CD_) gives its superclass, its properties (type, index, offset in the value table) and default values; an instance (CI_…/IL_) gives, for each property of its class and ancestors, two state bits, then a value table, then a heap of strings and arrays. Every length read in the files is bounded by the page or the record.

WINDOWS XP (python-cim's "XP" type, measured on the XP VMs): the names are hashed with MD5 (32 hexadecimal digits, an instance's class hash 0x40 bytes); a mapping's header is 16 bytes (no two identifiers) and its entries 4 (the physical page alone); the index's root is in the header of the index's logical page 0. The files are in Repository\\FS: the mappings in MAPPING1..2.MAP (SP2 and later), or in OBJECTS.MAP and INDEX.MAP, the same two mappings in two files (SP1).
