Detailed Description

THE table of the artefacts by version of Windows: where each one exists, where it lies and in which format, version after version.

WHY ONE TABLE (backlog B-039). An artefact exists only on some versions of Windows, at a place and in a format that change from one to the next: .evt then .evtx, Prefetch 17 then 30, index.dat then the WebCache, SRUM and Amcache from Windows 8, jump lists from 7, the search index in ESE then in SQLite. That knowledge was scattered in each collector. Here it is one table: adding a version of Windows is adding its line to RELEASES and, where something changed, a form to the artefacts concerned; nothing else in the code names a version.

THE ORDER OF THE VERSIONS IS THE BUILD NUMBER, client and server alike: 2600 (XP) < 3790 (Server 2003) < 6000 (Vista) < 7600 (7) < 9200 (8) < 9600 (8.1) < 10240 (10) < 22000 (11). An artefact is given its first build and, when it was withdrawn, the first build without it.

PRUDENCE. An absence is stated only when it is certain: one stated wrongly would lose an exhibit, a presence stated wrongly only costs an "expected but missing". Doubtful cases (Server Core, a service of the client editions on a server) stay present, their note saying what remains to be measured in the virtual machines of the compatibility items.

"EXPECTED" IS AS PRUDENT (ArtefactEntry::expectedSinceBuild). It is set only for a file or a key that every installation has AND that can be removed while Windows goes on: the hosts file, Amcache.hve, SRUDB.dat, the event logs, the Services key. It is NOT set for what exists only once something happened (USBSTOR, before the first USB storage), for the state of the running system (processes, sessions, connections) nor for the volume's own metadata ($MFT, $LogFile, $Secure): those cannot be missing from a running Windows, so one not read is a failed reading, never a trace.

A FORMAT IS RECOGNISED ON THE PIECE, by its signature or internal version (pieceFormat): the version of Windows says where to look, the piece says what it is. No collector keeps a version number of its own.

A VERSION NEWER THAN THE TABLE is treated as the last one known, and said so (WindowsRelease::known): the collection goes on.

Portable C++, without windows.h: tested natively (artefact_catalogue_test), which also writes the table of the documentation.

A path written in the folder layout of Windows Vista and later, as it lies on the examined version.

WHY. Every collector names its folders as Vista laid them out (<profile>\\AppData\\Local\\…, \\ProgramData\\…). Windows XP and Server 2003 keep the same data elsewhere: Local Settings\\Application Data, Application Data, Recent, My Documents, and the shared folders in All Users next to the profiles. Translated here, in one place, for the collection and the conversion alike, rather than by each collector.

A path under a profile is translated after that profile's folder; a path under \\ProgramData goes to the machine's All Users folder, which its ProfileList names (ProfilesDirectory and AllUsersProfile). Deduced from the first profile before, it was wrong on Server 2003: the system's profile comes first, under Windows\\system32\\config. From Vista on, or for a build not read (0), the path is returned as is.

versionthe examined Windows
profileRootsthe examined machine's profile folders, absolute
allUsersits All Users folder, with or without its letter
Returns
the path on that version

◆ pieceFormat()

PieceFormat pieceFormat ( const std::string & key,
unsigned signature,
const WindowsVersion & version = WindowsVersion{} )

THE FORMAT A PIECE STATES OF ITSELF. A collector asks it of every piece before decoding: the answer comes from the piece's own signature or internal version, never from the version of Windows — a Vista Prefetch found on a Windows 10 is a Vista Prefetch, and a $I of a version nobody has seen yet is not a $I version 2. A signature no form carries, or one of a form WAC does not convert, is NOT decoded: the piece stays collected raw and its JSON says "unsupported format" with the signature met — never a wrong conversion, never a silence. Adding a format is adding its form, with its signature, to the table.

Two releases can write the same signature with different contents — the ShimCache 0xBADC0FFE of Server 2003 and of Vista —: the examined version then picks the form, its own if it carries that signature.

Parameters
keythe key of wac.yml
signaturethe internal version or magic number read on the piece
versionthe examined Windows, for a signature several forms share; without it (build 0), the oldest form that carries it

THE FORMAT TOLD BY THE VERSION, when the piece cannot tell it itself: whether the form an artefact takes on a version is one WAC has no decoder for, while it converts another form of it — Amcache.hve without its Inventory keys before Windows 10 1607, BITS in qmgr0.dat before 1709, the search index in ESE before Windows 11.
