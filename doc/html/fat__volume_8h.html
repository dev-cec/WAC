Detailed Description

Raw reader of FAT12, FAT16, FAT32 and exFAT volumes.

WHY. A suspect's USB key, a memory card, an EFI system partition are FAT or exFAT: files named by the artefacts may lie there, and what was deleted there is still in their directories. NTFS's reader does not apply; the file system's API would not show the deleted entries, and would update access dates.

THE FORMATS, from Microsoft's specifications (FAT: "Microsoft Extensible Firmware Initiative FAT32 File System Specification", 2000; exFAT: "exFAT File System Specification", 2019), checked on volumes Windows formatted in the test VM against dissect.fat (Fox-IT):

  • FAT: a boot sector (sizes, FAT count, root), one or two FATs (the chains of clusters, 12, 16 or 28 bits by entry), the root directory (a fixed region in FAT12/16, a chain in FAT32), 32-byte entries — the long name in entries of attribute 0x0F before its 8.3 entry. A deleted entry has 0xE5 as first byte: its long name survives, bound to its 8.3 entry by a checksum, which also gives back the first letter lost;
  • exFAT: a boot sector, one FAT, an allocation bitmap, directories of entry sets (file 0x85, stream 0xC0, name 0xC1…): a deleted set only has the high "in use" bit of its types cleared — the whole name survives. Timestamps carry 10 ms and, when set, their UTC offset.

THE BYTES come from a VolumeSource: the volume itself during a collection, or the copy of what the collection read (its metadata — boot sector, FAT, directories —, never the files' content) during a conversion. Every read is bounded by the volume; every chain by the number of clusters, so that a looping FAT ends.
